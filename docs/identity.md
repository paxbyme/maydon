# Identity and resource access

The M3 backend uses email/password registration, single-use verification and recovery challenges, Argon2id (64 MiB, three iterations, one lane), and database-backed sessions. Registration and delivery requests return the same accepted response for known/unknown addresses. Redis atomically limits IP, account and SMS-target attempts; loss of Redis fails authentication mutations closed.

Access tokens expire after 15 minutes. Every protected request also checks the current session, account status and database roles. Refresh credentials are random 256-bit values stored as SHA-256 hashes. Rotation locks the user and session, consumes the old credential, and creates its successor without extending the original 30-day expiry. Reuse revokes the session in a committed transaction. Password reset revokes every session. Browser refresh credentials are Secure, HttpOnly, SameSite=Strict host cookies; rotation/logout require an exact allowlisted Origin and session-bound CSRF header. Mobile requests use explicit `client: mobile` and reject browser Origin headers. Clients must serialize refresh attempts: parallel retries intentionally trigger reuse revocation.

Challenges expire in ten minutes and allow five failed attempts. Codes use keyed hashes; delivery payloads use AES-256-GCM envelopes with purpose-separated HKDF keys. Password, session and challenge state changes are transactional with audit/outbox writes. Authentication responses have `Cache-Control: no-store`.

Administrators and any account with enrolled MFA cannot use protected operational routes until they complete TOTP in the current session. Removing an administrator role does not bypass an enrolled factor. Enrollment requires verified email and password proof. MFA secrets are encrypted with a separate derived key; accepted time steps cannot be reused. The TOTP implementation is checked against every SHA-1 vector in [RFC 6238 Appendix B](https://www.rfc-editor.org/rfc/rfc6238). MFA recovery and production administrator provisioning remain operational launch work; password reset deliberately does not remove an enrolled factor.

Resource permissions are checked from the owning business membership or one explicit staff assignment. Managers configure resources and operate bookings; clerks operate bookings and attendance; viewers can read operational/statistical views without contacts or mutation rights. Only owning business members can assign/revoke staff. Admin status alone does not grant resource operations; later administrative routes must require their own explicit authorization. Engineers have no application role. Future booking/calendar mutations must use the permission service inside their resource-locked transaction, and return contact fields only after a separate `contact` permission check.

## Local delivery

`node scripts/init-local-env.mjs` creates an ignored mode-0600 `.env` with a random secret and never overwrites an existing file. Docker Compose loads the root environment when run from the repository root. For host API processes, supply the environment explicitly; Node does not implicitly load `.env`.

Only the local adapter is implemented. The worker writes mode-0600 JSON messages to `DEV_DELIVERY_DIR` (mode-0700 directory), marks them `LOCAL_TEST_ONLY`, and deduplicates by event key. No OTPs are logged or exposed through an API mailbox. Container messages reside in `/app/dev-mailbox` in the worker. Local files are development credentials: remove them when no longer needed. Real SMS/email integrations, delivery retention and key-rotation procedures are release gates. Production startup remains disabled.

`AUTH_SECRET` is required for API and worker startup. `WEB_ORIGINS` defaults to the three local app origins on ports 5173–5175. Schema export uses an ephemeral key only if no key is configured; it never listens on a network port. Dedicated Docker tests use a visibly test-only key, no host ports and disposable database/Redis storage.

## Client identity implementation

All apps use `packages/identity`: generated operations, shared forms and one session controller. Access tokens remain in memory. Mobile refresh credentials use flutter_secure_storage 9.2.4 with iOS device-only unlocked Keychain accessibility and Android encrypted preferences; Android backup is disabled to avoid restoring ciphertext without its device key. Browser code never uses the secure-storage web implementation or local/session storage for credentials. Browser rotations are serialized within each app and across same-origin tabs with Web Locks. Failed protected mutations are not replayed automatically. A failed logout remains visibly signed in until the server confirms revocation.

Language preference uses shared_preferences 2.5.3 for non-sensitive device preference only. On sign-in the account locale is adopted; language changes while signed in update the account after local persistence. All forms provide localized labels, validation and safe errors; raw server exception text is never displayed. MFA enrollment secrets exist only in the active form and are cleared on navigation/completion.

For local web use stable ports 5173 (player), 5174 (owner), 5175 (admin), supplied by `scripts/run-flutter.sh`. API defaults to localhost:3000, or 10.0.2.2:3000 for Android emulator. Override with `--dart-define=MAYDON_API_URL=https://your-api-origin`. Android debug builds permit local cleartext; release builds require HTTPS. iOS permits local networking without globally disabling transport security.

Deploy each web app with its API proxied under the same origin: the non-HttpOnly CSRF cookie must be readable by that app, while refresh credentials remain HttpOnly. Local ports share localhost cookies; separate browser profiles isolate accounts when testing several apps concurrently. Web Locks require a secure context (HTTPS or localhost). The local-delivery notice defaults on; only an approved real-delivery deployment may set `MAYDON_LOCAL_DELIVERY=false`.

Reference package behavior: [secure storage 9.2.4](https://pub.dev/packages/flutter_secure_storage/versions/9.2.4), [preferences 2.5.3](https://pub.dev/packages/shared_preferences/versions/2.5.3). Production provider and release gates still apply.
