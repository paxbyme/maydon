# M5 — owner onboarding, facilities and discovery

State: in progress. Owner application, manual review, private facility drafts and sports catalog flows implemented; M5 is not accepted.

## Available flow

Verified owners submit a registered business name and private ownership evidence notes from the owner Overview or Facilities tab. Applications appear as pending, approved or requiring changes. Rejected applications can be corrected and resubmitted. One pending application per applicant is enforced under a user-row lock.

MFA-verified platform administrators use Applications to read private evidence and approve or reject with a reason. Administrators cannot review businesses they belong to. Decisions lock the application row, require pending status, and atomically commit audit records and an in-app notification outbox event. Evidence access is audited. Previous decision reasons are retained as encrypted audit envelopes when a rejected application is resubmitted.

Evidence notes are encrypted with a purpose-separated AES-GCM key. List responses exclude evidence; private endpoints return `Cache-Control: no-store`. Evidence notes are an initial review input, not a substitute for the document-upload workflow still required below. No automatic owner approval or facility publication is implemented.

Approved owners can open **Manage facilities** on their business card, create private Namangan drafts and edit drafts or rejected facilities. Each draft has an address, coordinates and one to three localized names/descriptions. The owner list falls back to an available translation when the current UI language is absent. The editor never publishes a facility. Pending, approved and suspended facilities cannot be changed through this draft endpoint.

Edits carry the last observed revision. Competing edits accept one revision and return 409 for stale copies; failed saves keep the owner's input. Reads remain available to owning members when a business is not approved, but write controls are hidden and writes are denied server-side.

The player Explore page now displays the active sports catalog without sign-in. Names switch with the UI language, and pagination/error states preserve already loaded entries. This is a catalog, not a working venue filter: discovery awaits publication and resource readiness.

MFA-verified administrators can open **Manage sports** from Overview, add sports with all three translated names, rename them and activate/deactivate them. Identifiers are immutable; revisions reject competing stale edits. Deactivation hides a sport from the public catalog without deleting resource or game references. Incomplete legacy entries remain available to administrators but are excluded from the public list.

## Data and contract

Migration `202611020001_owner_evidence` adds nullable `OwnerProfile.evidenceCiphertext` without changing existing records. Existing applications without evidence cannot be approved through the new API.

- `GET /api/v1/businesses`: own applications, cursor pagination, 25 per page.
- `POST /api/v1/businesses`: verified applicant submits a pending application.
- `PUT /api/v1/businesses/:id/submission`: owning verified member resubmits a draft/rejected application.
- `GET /api/v1/admin/businesses`: MFA-verified administrator's pending queue.
- `GET /api/v1/admin/businesses/:id/evidence`: audited private evidence read.
- `PUT /api/v1/admin/businesses/:id/review`: audited approval/rejection with reason.

Migration `202611020002_facility_revision` adds a positive, default-one revision to existing facilities.

- `GET /api/v1/businesses/:ownerId/facilities`: owning members only, 25 per cursor page, explicit `canEdit` capability.
- `POST /api/v1/businesses/:ownerId/facilities`: verified member of an approved business creates a draft; Namangan and Asia/Tashkent are server-owned defaults.
- `PUT /api/v1/businesses/:ownerId/facilities/:id`: draft/rejected editing only, requires `expectedRevision`, approved ownership and verified email.

Migration `202611020003_sports_catalog` adds a positive sport revision and seeds football, basketball, volleyball and tennis in uz/ru/en, preserving any existing slugs, activation choices and translations.

- `GET /api/v1/sports`: guest access to active, fully translated sports, 25 per cursor page.
- `GET /api/v1/admin/sports`: MFA-verified administrator list including inactive entries.
- `POST /api/v1/admin/sports`: audited creation with unique immutable slug and complete translations.
- `PUT /api/v1/admin/sports/:id`: audited names/activation update with `expectedRevision`; existing references survive deactivation.

The generated Dart client now supports typed arrays and scalar query parameters, including nullable pagination cursors. Owner/admin screens use generated operations and existing authorized session handling. All new labels and errors are localized in Uzbek Latin, Russian and English.
